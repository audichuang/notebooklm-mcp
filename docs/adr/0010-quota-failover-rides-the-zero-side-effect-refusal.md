# Quota failover rides the zero-side-effect refusal, and only that

A Google One family plan puts several paid NotebookLM accounts behind one owner, so daily generation quota can be pooled instead of being a hard daily ceiling on one account. The server therefore accepts N credentials (`NOTEBOOKLM_AUTH_JSON`, `_2`, `_3`, …, all injected by Doppler from a single config) and holds N long-lived clients in one process. Installation, MCP registration and every tool call site are unchanged: `runtime.get_client()` keeps returning "the currently active client", so the pool is invisible above `runtime.py`.

**Failover is attached to exactly one `except` clause** — `_REFUSED_WITHOUT_DISPATCH = (RateLimitError, ArtifactFeatureUnavailableError)` in `tools_podcast.py`. That tuple is the only place in the system where the contract guarantees the remote built no task: a quota-exhausted account refuses **synchronously** (measured: 1.35s between `dispatch.dispatched_at` and `remote.observed_at`, `dispatch.status=not_accepted`, `remote.artifact_id=null`). Rotating the client and re-sending is therefore idempotent, and it re-sends **the same attempt** — same `attempt_id`, no supersede, no new manifest record. This is deliberately *not* "regenerate the episode with another account".

**Everything after dispatch keeps its current behaviour.** The `status="removed"` path (an accepted artifact later taken down by the server, `audio_finalize.py`) looks like a quota problem and is not the same thing: by then a task exists, so switching accounts would mean retracting an attempt and writing a replacement — i.e. the MCP silently rewriting the manifest's causal record, which is precisely what ADR-0009 forbids. Those failures still return the existing safe stop point and let the host decide. The AGENTS.md gotcha that reads "quota exhaustion usually shows up as `removed`" describes that later path only; it is not the shape of a refusal at kickoff.

**Transparency stops at the audit trail.** The client is not told which account served a call, but the manifest is: the dispatch record carries `account`, and every rotation appends to `errors[]` ("A refused → retried on B"). Without this, "which account produced EP35" and "which account is out of quota" both become unanswerable, and a dying cookie is masked instead of surfaced — a pool that silently absorbs an expired credential will keep absorbing them until none are left.

**Provisioning constraints.** Credentials with `$` in cookie values are corrupted silently by `doppler secrets upload` (variable interpolation strips them; a 16137-byte state came back as 16103 bytes of invalid JSON), so every credential is written with `doppler secrets set --raw` and verified by an actual RPC, not by byte comparison. A branch config inherits its root's unset secrets, so `dev_alt` — whose `NOTEBOOKLM_AUTH_JSON` is account 2 — would inherit `dev`'s `_2` and pool the same account twice; it is deleted when the pool lands rather than left as a trap.

Cross-account collaboration was measured before any of this was designed, on a throwaway notebook: an EDITOR can add sources to someone else's notebook and delete sources **added by others** (ADR-0009's cleanup precondition survives account rotation), and artifacts and sources are visible in both directions, so `artifact_ids_before` reconciliation holds across accounts. That is why the manifest schema needs one new field and no structural change.

**Quota is charged to the caller, not to the notebook owner — this is now measured, not assumed.** In the v0.8.0 acceptance run the owning account's daily quota ran out mid-series; the refusal arrived in 1.43 seconds, rotation moved to the second account, and that account — an EDITOR on someone else's notebook — was accepted 4.4 seconds later. Had quota been charged to the owner, rotating the caller would have accomplished nothing and this entire decision would be void. All three staging accounts were then exhausted in turn, exercising both hops (A→B, B→C) and confirming that per-process rotation never walks back into a spent account.

Two preconditions the original design did not state, both found by that run:

**The active credential is the download identity.** notebooklm-py re-reads `NOTEBOOKLM_AUTH_JSON` at download time rather than using the client's own session, so the pool cannot treat that variable as a scratch slot during construction — it must always equal the account currently in use, including after a failover. Getting this wrong pointed every download at whichever account happened to occupy the last slot, and the symptom (401 during finalize) surfaced a quarter of an hour after the cause. Until the SDK downloads through the client's session, "one process, N accounts" rests on that variable being right at every instant.

> **Amended in v0.9.0 — that last sentence was the bug, not the fix.** "Right at every instant" is unachievable in this server: MCP dispatches every incoming message with `tg.start_soon`, so tool calls interleave at each `await`, and no amount of locking makes one global slot simultaneously hold two values. A long `_finalize_episode` pinning client A while a concurrent episode rotates to B is not a race to be narrowed — it is the normal case. The variable was retired as an identity: each pooled account is now written to its own `0600` storage-state file and built with `from_storage(path=…)`, which the SDK injects into the download service (`_client_assembly.py` → `ArtifactsAPI(storage_path=…)`), so identity travels with the client and the env var is never written by this server at all. Two consequences worth stating. The credential now exists on disk for the server's lifetime — accepted because any user who could read that `0700` directory could already read `/proc/<pid>/environ`, and the directory is removed on every exit path. And giving the SDK a real path re-arms its **L2 inline PSIDTS `RotateCookies` recovery**, which — unlike the keepalive poke — has no env switch; it is reachable only from the strict cookie loader's `ValueError`, so each credential is validated *before* being written, keeping that branch unreachable and preserving the "never re-mint cookies in this process" rule that three VMs sharing one read-only Doppler credential depend on. **That unreachability rests entirely on the pre-check and the strict loader agreeing, and the first version of it did not** — `extract_cookies_from_storage` accepts a required cookie whose value is an empty string (it only checks the name); the strict loader treats empty as absent. A blank `__Secure-1PSIDTS` therefore passed the pre-check, raised on open, and fired a real `RotateCookies` POST — reproduced end to end. The pre-check now asserts non-empty values too, and `test_precheck_agrees_with_the_sdk_strict_loader` pins the equivalence in both directions, because that assumption is the whole load-bearing claim and nothing else was guarding it. One residual asymmetry is documented rather than chased: for a same-named cookie across domains, the two disagree on which entry wins, and we fail closed (loudly, at startup).
>
> The same amendment covers accounting. `_claim_prepared_dispatch(account=…)` and the actual `generate(client)` used to be two separate global reads, and `_rotate_for_quota` read `from_account` *after* the dispatch await had already given a concurrent call the chance to rotate — so the manifest could credit an account that took no part in that dispatch, undetectably, since both accounts succeed. Callers now take one `runtime.snapshot()` and thread `(label, client)` through failover together.

**The notebook must be reachable by the whole pool, and nothing in this design establishes that.** A notebook created through MCP belongs to the account that created it; rotation then sends the retry to an account that cannot see it. Permission denial is now classified as `NotebookAccessDenied` (a `RuntimeError` subclass, so both dispatch call sites already treat it as a clean no-task-created terminal) with a message naming the fix, and rotation deliberately stops there — an ACL gap is a configuration problem, and trying each account in turn would only bury it. **Who creates that shared state remains undecided**; today it is the operator's job, performed out of band.

Status: implemented and exercised against real accounts. Staging (`stg`) deliberately runs *free* accounts — low quota is a feature there, because exhausting it is the only way to exercise this path repeatably. It started at three; it now carries **seven free accounts plus two paid fallbacks in the last two slots**, because one full acceptance round costs 6–8 generations and three free accounts (≈9/day) meant waiting for an unobservable quota reset between rounds. Slot order is load-bearing: rotation walks front to back, so a normal round only ever spends free quota, and reaching the fallbacks means the day's seven free accounts are already gone. Those two are the *same accounts* as `prd`'s `_4`/`_5`, so spending them eats into the next day's production capacity — which is exactly why they sit last rather than first.
