# Quota failover rides the zero-side-effect refusal, and only that

A Google One family plan puts several paid NotebookLM accounts behind one owner, so daily generation quota can be pooled instead of being a hard daily ceiling on one account. The server therefore accepts N credentials (`NOTEBOOKLM_AUTH_JSON`, `_2`, `_3`, …, all injected by Doppler from a single config) and holds N long-lived clients in one process. Installation, MCP registration and every tool call site are unchanged: `runtime.get_client()` keeps returning "the currently active client", so the pool is invisible above `runtime.py`.

**Failover is attached to exactly one `except` clause** — `_REFUSED_WITHOUT_DISPATCH = (RateLimitError, ArtifactFeatureUnavailableError)` in `tools_podcast.py`. That tuple is the only place in the system where the contract guarantees the remote built no task: a quota-exhausted account refuses **synchronously** (measured: 1.35s between `dispatch.dispatched_at` and `remote.observed_at`, `dispatch.status=not_accepted`, `remote.artifact_id=null`). Rotating the client and re-sending is therefore idempotent, and it re-sends **the same attempt** — same `attempt_id`, no supersede, no new manifest record. This is deliberately *not* "regenerate the episode with another account".

**Everything after dispatch keeps its current behaviour.** The `status="removed"` path (an accepted artifact later taken down by the server, `audio_finalize.py`) looks like a quota problem and is not the same thing: by then a task exists, so switching accounts would mean retracting an attempt and writing a replacement — i.e. the MCP silently rewriting the manifest's causal record, which is precisely what ADR-0009 forbids. Those failures still return the existing safe stop point and let the host decide. The AGENTS.md gotcha that reads "quota exhaustion usually shows up as `removed`" describes that later path only; it is not the shape of a refusal at kickoff.

**Transparency stops at the audit trail.** The client is not told which account served a call, but the manifest is: the dispatch record carries `account`, and every rotation appends to `errors[]` ("A refused → retried on B"). Without this, "which account produced EP35" and "which account is out of quota" both become unanswerable, and a dying cookie is masked instead of surfaced — a pool that silently absorbs an expired credential will keep absorbing them until none are left.

**Provisioning constraints.** Credentials with `$` in cookie values are corrupted silently by `doppler secrets upload` (variable interpolation strips them; a 16137-byte state came back as 16103 bytes of invalid JSON), so every credential is written with `doppler secrets set --raw` and verified by an actual RPC, not by byte comparison. A branch config inherits its root's unset secrets, so `dev_alt` — whose `NOTEBOOKLM_AUTH_JSON` is account 2 — would inherit `dev`'s `_2` and pool the same account twice; it is deleted when the pool lands rather than left as a trap.

Cross-account collaboration was measured before any of this was designed, on a throwaway notebook: an EDITOR can add sources to someone else's notebook and delete sources **added by others** (ADR-0009's cleanup precondition survives account rotation), and artifacts and sources are visible in both directions, so `artifact_ids_before` reconciliation holds across accounts. That is why the manifest schema needs one new field and no structural change. Whether quota is charged to the caller or to the notebook owner is an operator-confirmed assumption, not a measured one — if it were charged to the owner, rotating the caller would accomplish nothing and this entire decision is void.

Status: pool and rotation are being implemented; the design above is fixed. Staging (`stg`) deliberately runs three *free* accounts — low quota is a feature there, because exhausting it is the only way to exercise this path repeatably.
